For assignment 1  I created a Cat knowledge quiz because I like cat and I think it would be a fun topic, the questions are about cat behaviors, communication, and some basic facts about cats.
The game randomly picks 5 questions from a JSON file. Some questions have one correct answer, and some have two. Players get 10 points for each correct question and 5 extra points if they answer within 5 seconds. At the end, the game shows their final score and gives them a title based on how well they did.



1. Data Structure Justification
For storing the quiz questions I used a JSON file with a dictionary, and inside each question there's another dictionary that has the options, answers, and a fun fact. I also used a separate JSON file for the scores, which is just a dictionary with the player's name and their best score. I picked this because it's really easy to read and edit. For example, if I want to add a new question, I can just open the JSON file and add it, I don't have to change the Python code at all. Also, since the answers are in a list, I can have questions with one correct answer or two correct answers, and the code just checks how many are in the list. Another important reason is that each question’s options, correct answers, and fun fact are kept together in one object, so adding or changing a question does not cause data misalignment.  The main goals were that it's readable for humans, easy to maintain, and works well with the program. If I used separate lists for options and answers, it would be a mess to keep them in sync.
2. Function Design
The main non-trivial custom function I designed is get_answer(options, letters, message). It keeps asking the user until they type something valid. It also strips spaces and makes it lowercase so "A" and "a" both work. Then it turns the letter into the actual option text. I made it like this because I didn't want to write the same input checking code over and over for every question. I designed it this way because both single-answer and two-answer questions need the same validation and letter-to-option conversion. If I wrote that logic separately for each question, the code would be repetitive and easier to break. By returning the option text instead of the letter, the main quiz loop can compare the user’s choice directly with the answers list. This makes the function reusable, keeps the main program cleaner, and makes the quiz logic easier to read and test.
3. Control Flow
For invalid inputs, I put a while loop inside get_answer() that keeps asking until the answer is not empty and is in letters[:len(options)]. For example, if a question has only four options, the user can only enter a through d, not e or f. I chose this loop structure because invalid input is a normal user mistake, not a program error, so the program should re-prompt instead of exiting or crashing. For two-answer questions, there is an extra while loop that prevents the second answer from being the same as the first, which keeps the quiz fair and correct. The main goals here were to make it robust so it doesn't crash, and to be user-friendly so people know what they did wrong. Also, it's consistent because every question uses the same validation. So no matter what question comes up, the input handling is the same.
